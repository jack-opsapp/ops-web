## 2026-07-15 assignment-safe follow-up — contact form → assigned review draft

- **Plan:** `docs/plans/2026-06-03-inbox-forwarded-form-new-thread.md`

**Current contract:** a website contact-form submission forwarded into a connected mailbox must never create a reply on the forwarder's provider thread. OPS creates or matches the lead first, preserves the exact mailbox/message/thread/activity identity, and starts a **clean new provider draft to the actual client** only after a canonical OPS user is the lead's current assignee. The first outreach is always review-only; this worker has no send capability.

**How:** company-mailbox ingestion leaves the lead unassigned. Personal-mailbox ingestion may assign only the connection's active canonical OPS owner through the guarded assignment operation. Migration `20260715178000_email_assignment_contact_form_drafts.sql` rendezvouses the immutable current assignment event with the exact inbound activity in a service-only queue. Migration `20260727005232_bridge_contact_form_draft_recipient_provenance.sql` keeps the source activity untouched while deriving the recipient from the opportunity's canonical contact email, falling back to the active linked client only when the opportunity email is blank. A retained internal-forwarder sender is accepted only after the service ingestion boundary re-proves its deterministic contact-form parser result against the exact activity, connection, lead, provider message, provider thread, and canonical recipient, then records that fact as immutable private provenance. Assigned operators can continue recording ordinary lead provenance, but editable public provenance alone never authorizes this path. Conflicting lead/client identity fails closed. The same exact-source proof is repeated by the existing claim, preparation, reauthorization, provider-reservation, and completion gates. The worker also rechecks assignment version, active user, canonical lead edit authority, `inbox.send`, active mailbox transport, the exact message-scoped lead key, and `primary:CUSTOMER` autonomy immediately before provider draft creation. Company connector `user_id` is ignored; only `type='individual'` may use its exact owner as transport authority.

**Forward-only scope:** the migration performs no historical queue replay and trusts no pre-migration wrapper evidence. New source activities, guarded orphan-adoption transitions, service attestations, and later assignment events rendezvous idempotently. Any older raw-wrapper row remains skipped unless it is deliberately reprocessed through the guarded ingestion path.

**Source-bound routing:** the forwarding platform's notification thread is not treated as a customer conversation. The assignment queue may stand in for the absent durable customer thread only when the draft service independently reloads the exact source activity and receives canonical send access for the same actor, company, connection, and opportunity. The submitted name, message, and email remain inside the untrusted-data envelope; only a fixed server-owned purpose is treated as instruction. This path persists no reply provenance (`thread_id` and `source_message_id` remain null), always uses the server-owned new-thread subject `Thanks for reaching out`, and fails closed on every source or authorization mismatch. Learned, generated, and operator-provided subjects cannot override it. Ordinary conversation drafts continue to use the canonical thread router.

The model uses the assignee's `client_new_inquiry` learning profile. The body is rendered with the effective signature in this order: operator-scoped OPS signature, mailbox-wide OPS signature, then a supported provider signature. An unsigned contact-form review draft is intentionally placed so the operator can review it; OPS keeps signature reconciliation actionable without blocking that draft.

**Atomicity and reconciliation:** after provider acceptance, one database transaction locks the opportunity and queue, rechecks the current assignment and autonomy, activates only the current assignee's Phase C history, links the new provider thread, and completes the queue row. Once a provider-create attempt begins, an uncertain provider result or failed OPS completion is quarantined as `reconciliation_required` for human action. The worker does not inventory or adopt provider drafts automatically and never retries an ambiguous create. A later human send is reconciled from the immutable provider message/thread identity; edit learning must pass the assignment-aware outbound-learning authorization added by the July 2026 hardening chain.

**Verification contract:** canonical-recipient attestation, service-only ACL, immutable exact-source binding, forward orphan adoption, no-historical-replay, source-bound authorization, untrusted-content isolation, worker, runtime, mailbox-placement, provider-failure, signature, fixed-subject, reassignment, idempotency, and no-send tests are included in the July 2026 email hardening suite. Verification never creates or sends a real Gmail/Outlook message.

**Live acceptance (run only after the complete migration chain and reviewed Operator activation are deployed):** ingest a real contact-form submission into company and individual Gmail/Outlook connections; verify the company lead stays unassigned and produces no draft until guarded assignment, the individual lead assigns only to its active owner, and the resulting item is a new review draft to the canonical customer. Verify the fixed subject, effective-sender path, exact service-attested internal-forwarder path, forged public-provenance rejection, guarded orphan adoption, signature precedence, unsigned draft placement while signature reconciliation continues, reassignment before/after provider acceptance, `reconciliation_required` quarantine for uncertain provider acceptance, edit + native send reconciliation, and that no automated send occurs. Repeat the manual Pipeline **Draft** path on both providers.

## Release blockers and explicit limitations

- Do not enable the Operator preset until its reviewed activation migration lands after the complete email chain. The absent activation is intentional and keeps new assigned-scope behavior fail-closed.
- Assignment-event Realtime fan-out, child-table scoped RLS, and strict permission transports must use their independently reviewed parent-task migrations. Do not recreate those contracts in email code.
- A provider and Postgres cannot share one transaction. If assignment changes after the final pre-provider draft check but before provider acceptance, OPS rejects all attribution and learning; the unlinked, unsent provider draft may remain quarantined in Drafts. Release monitoring must expose these rare orphaned provider drafts for operator cleanup.
- Provider uncertainty has no automatic inventory/adoption path. Any `reconciliation_required` row needs human review before another provider create can occur.
- Production completion requires the complete reviewed migration order, deployment, live policy/function readback, real-mailbox acceptance on both providers, and proof that no unauthorized provider send occurred. Local green tests are not production proof.
